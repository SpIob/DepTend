## Phase 1 — lock mechanics (two real concurrent sessions, no data changes)

```json
{
  "hashes": { "repo_key_hash": "-542550332", "other_key_hash": "-1206255066" },
  "lockWhileHeld": [{ "locktype": "advisory", "key_hash": "3752416964", "granted": true }],
  "blockedSameKey": { "result": "blocked", "pg_code": "57014", "waited_ms": 4084 },
  "otherKeyUnaffected": { "result": "acquired", "waited_ms": 41 },
  "afterReleaseInstant": { "result": "acquired", "waited_ms": 40 },
  "waitedThenAcquired": { "waited_ms": 1245 }
}
```

| Step                                                | Expectation                                    | Result                                     |
| --------------------------------------------------- | ---------------------------------------------- | ------------------------------------------ |
| A holds lock in open txn                            | advisory lock visible in `pg_locks`, `granted` | ✅ (`3752416964` = `-542550332` as uint32) |
| B acquires SAME key under 4s `statement_timeout`    | blocks, then 57014 cancel                      | ✅ blocked, cancelled after 4084 ms        |
| B acquires a DIFFERENT key while A holds            | immediate (per-repo granularity)               | ✅ 41 ms                                   |
| A ROLLBACKs; B retries same key                     | instant acquire (xact-scoped auto-release)     | ✅ 40 ms                                   |
| B acquires with NO timeout; A releases ~1.2 s later | B waits, then proceeds without error           | ✅ waited 1245 ms, then acquired           |

The lock blocks same-key acquirers, does not contend across repos, releases
automatically on transaction end, and a blocked writer proceeds the moment the
holder commits/rolls back — exactly the semantics the writer relies on.

## Phase 2 — end-to-end 10-way concurrent writer race (the ADR's load-test claim)

Fixture's 8 missions + 8 score rows cleared first (synthetic, regenerated by the
code under test; dev totals before 310 missions / 310 scores). Then 10 concurrent
real `generateMissionsForRepo()` calls via `Promise.all`:

- All 10 writers completed, **0 errors**, race wall time 3195 ms.
- Writer 0: `created=8`. Writers 1–9: `created=0, updated=8` each — serialized by
  the lock, first set wins, the other nine refreshed the same rows.
- `sumCreated = 8` — exactly one creator.
- Post-state: 8 mission rows, `count(DISTINCT (dependency_id, advisory_id,
mission_type)) = 8`, 8 mission_scores, dev totals back to 310.

`assertions: { exactlyOneSet: true, scoresComplete: true, exactlyOneCreator: true,
noWriterErrors: true }`

Sequential re-run afterwards: `created=0, updated=8, resolved=0` — re-run safety
contract intact (ADR 0008 §2: refresh without touching status/claims).

Post-race fixture integrity (via Neon MCP): the 8 missions map back to exactly the
8 pre-race OSV advisories (GHSA-3pqx-4fqf-j49f, GHSA-6757-jp84-gxfx,
GHSA-8q59-q68h-6hv4, GHSA-rprw-h62v-c2w7, PYSEC-2018-49, PYSEC-2020-96,
PYSEC-2020-176, PYSEC-2021-142), all `vulnerability_fix` / `open`.

## Conclusion

Both previously-uncorroborated Verification bullets in ADR 0057 are now
corroborated against real Postgres:

1. _Concurrent `generateMissionsForRepo` calls — no duplicate missions:_ ✅
   (10-way race, exactly one set of 8, zero duplicate triples).
2. _10 concurrent runs — exactly one set of missions created:_ ✅ (`sumCreated = 8`).

Scope note: this proves the lock's behavior under deliberate overlap. It does not
assert that a production cron overlap has occurred in the wild — the ADR's threat
model is the stalled-run / cron-plus-manual case, which is synthetic by nature.

Dev-branch side effects: none remaining (fixture regenerated to its pre-probe
state; the only mutation was the deliberate clear-then-race of regenerable
synthetic rows).
