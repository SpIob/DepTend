# ADR 0068: Fix-PR Link on Claimed Missions

**Status:** Proposed (implemented 2026-11-18; migration applied to both Neon branches same day — flip to Accepted after a live signed-in write is observed on production, per §10's live-verification rule)
**Date:** 2026-11-18
**Decided by:** Mico (Option 1 of issue #42's three options, chosen 2026-11-18)

---

## Context

A claimed mission had nowhere to point at the fix. The claimant opens a PR in their fork or the upstream repo, and the mission card kept saying "claimed by @user" until someone manually noticed the merge. The rescue board's loop closes only when the fix lands, and nothing linked the two.

Issue #42 flagged this as a **decision point rather than a normal issue** because it needs a schema change (AGENTS §0.3), and `missions` has deliberate quirks the write path must respect (no unique constraint; manual SELECT-then-INSERT/UPDATE writes per AGENTS §8). Three options were on the table:

1. **Nullable `missions.pr_url` (+ `pr_url_added_by`)** — one migration, one guarded single-statement UPDATE (the §7 `claimMission()` template).
2. **`mission_links` table** (mission_id, kind, url, added_by) — extensible to comments/screenshots later.
3. **Do nothing** — claimants coordinate in the upstream repo; DepTend stays read-only about outcomes.

## Decision

**Option 1.** Option 2's extensibility is speculative until a second link kind actually exists; option 3 leaves the rescue loop unclosed for the want of two nullable columns.

## Implementation

- **Migration `0010_mission_pr_link`**: `ALTER TABLE missions ADD COLUMN "pr_url" text;` + `ADD COLUMN "pr_url_added_by" text;` — both nullable, no index, no enum change. Generated by `drizzle-kit generate` from schema.ts; applied to the dev and production Neon branches on 2026-11-18 (ledger + live-catalog cross-checked per AGENTS §12).
- **Write path** (`packages/core/src/db/missions.ts::setMissionPrUrl`): a single guarded UPDATE whose WHERE carries `status = 'claimed' AND claimed_by = $login` — the same claimant-ownership rule as `unclaimMission`, enforced by the database, not by a read-modify-write. Clearing (`prUrl = null`) uses the identical guard; `pr_url_added_by` is stamped on set and cleared on clear. Outcomes: `"updated" | "not_claimed_by_you" | "not_found"`, following the project's exhaustive outcome-typed convention.
- **URL validation** (`packages/core/src/pipeline/parse-pr-url.ts`): sibling of ADR 0066's `parse-github-url.ts` — strictly `https://github.com/owner/name/pull/N` (trailing slash tolerated, normalized away). Runs at the route boundary; the route's test suite exercises the real parser (kept via `importOriginal`, per the route-test discipline).
- **Route** (`POST /api/missions/[id]/pr-link`): body `{"prUrl": string | null}` — a string sets the link, `null` clears it. Full gate stack per ADR 0037 (same-origin → session → shared `checkMissionActionLimit` rate limit → uuid), colocated `route.test.ts` with both origin paths. Success revalidates **only the `missions` tag**: the link renders on board cards and the permalink, but the directory's severity counts don't read it (claim/unclaim revalidate `repos` too because they change those counts — this write doesn't).
- **UI**: the claimed-by-me branch of `MissionActions` gains an inline editor (input + save; empty input = clear); `MissionMeta` renders a "fix PR ↗" link on any card whose mission carries a `pr_url` — including the `claimed-by-other` case, where the point is for _others_ to see the fix in progress. The client-side patch type is a `MissionPatch` union (`MissionClaimPatch | MissionPrUrlPatch`) so the board's optimistic state update handles both without weakening the claim patch's required-field contract.

## Consequences

- The mission model now carries outcome data for the first time (previously deliberately read-only about outcomes — option 3's stance). Kept deliberately minimal: one URL, one stamp. If a second link kind (screenshots, comments) ever materializes, a `mission_links` table can absorb the single use case without a destructive migration.
- Only the _current_ claimant can set or clear; a mission claimed by someone else cannot be annotated by a previous claimant (the WHERE clause fails → 409). This matches the trust model: the link is a claim _about work in progress by the claimer_, not a free-form comment field.
- `pr_url` survives auto-resolution (the row keeps its history), but resolved missions don't render on the board, so the display surface is claimed missions — and the permalink.
