# ADR 0054: 2026-09-05 production audit fixes (a11y, /api 404, page-clamp)

**Status:** Proposed
**Date:** 2026-09-05

---

## Context

A 2026-09-05 end-to-end audit of the production site (`deptend.vercel.app`) surfaced three real defects, each independently fixable but batched here because they were all found in the same audit pass and each affects a different surface (a11y, API surface, page rendering). All three were verified live against the deployed site before this ADR was drafted.

### Finding 1 — Bookmark buttons share one `aria-label`

Both `RepoCard` and the per-repo page render a `<BookmarkToggle>` next to the repo name. On the homepage (`/`) the directory list renders four cards; each one's `BookmarkToggle` had `aria-label="Sign in with GitHub to bookmark this repo"`. A screen reader navigating the four buttons in sequence heard the same label four times in a row with no way to tell which one was which. Same shape on `/org/SpIob` (3 cards) and on the per-repo page if a future layout ever places a second toggle.

`NotificationToggle` had a parallel issue: its `aria-label` was a hard-coded string and its signed-in state had no `aria-label` at all (only a `title`), so the signed-in button read identically to "no label" to a screen reader in some browsers.

### Finding 2 — Unmatched `/api/*` paths return 200 with HTML

`POST /api/repos/precheck` (a path that doesn't exist) returned HTTP 200 with `content-type: text/html` and the 404 page's body. The previous Vercel audit (ADR 0048) fixed the same shape for top-level page routes — `/totally-not-a-real-page` now renders the styled 404 — but `/api/*` was not in scope, and Next 15.5's catch-all behavior is "no matching file, fall through to the top-level 404 page with the default status, which is 200" specifically for routes under `/api/`.

Failure mode for a client: `await fetch("/api/whatever", { method: "POST" })` resolves to a `Response` whose `.ok` is `true` (200 is in 2xx), then `await res.json()` throws because the body is HTML. The two-step error means callers that wrap the fetch in a `try/catch` get a SyntaxError instead of a meaningful 404, and callers that only check `.ok` silently proceed with the wrong assumption that the request succeeded.

### Finding 3 — Out-of-range `?page=` flashes an empty board before the redirect resolves

`/missions?page=99` (against a 4-page board) renders an empty board with the page header still visible. The page then redirects to `?page=4` via a `<meta http-equiv="refresh">` because `redirect()` from a streaming Server Component cannot commit a real HTTP 307 once the RSC stream has started flowing. The redirect itself works, but the user sees ~1 second of empty content first, and the URL bar keeps `?page=99` for that second. This is the same meta-refresh-fallback pattern that the `isCanonicalMissionBoardQuery` redirect uses for `?sort=easiest` and friends — it's a known App Router behavior, not a misconfiguration.

The `isCanonicalMissionBoardQuery` redirect on the same page is fine for the `?sort=easiest` case (the redirect is the first thing the page does, before any data fetch, so the empty-flash window is shorter and there's no data displayed to "wrong-render"). The `page > pageCount` redirect runs _after_ the data fetch, so the user sees the empty board first.

## Decision

Three small, idiomatic fixes — one per finding. No new dependency, no schema change, no new query, no contract change for the existing real API routes. Each fix is the minimum surface that makes the bug go away and is unit-tested at the smallest meaningful boundary.

### 1. Make `aria-label` repo-specific on both toggles

`BookmarkToggle` and `NotificationToggle` each take a new required `repoFullName: string` prop (`"owner/name"`). The signed-out `aria-label` becomes `"Sign in with GitHub to bookmark ${repoFullName}"` (and the equivalent for notifications); the signed-in label flips between `"Bookmark ${repoFullName}"` / `"Remove bookmark for ${repoFullName}"` (and the subscribe/unsubscribe equivalent). Both call sites — `RepoCard` and the per-repo page — already have `repo.owner` and `repo.name` in scope, so the prop is filled in without any new data flow. The `title` attribute is updated in lockstep with `aria-label` for sighted-user consistency.

Mirrored on `NotificationToggle` because the same multi-card page renders both toggles and the same a11y regression would resurface the moment a layout puts N notification toggles in a row.

### 2. Add `/api/[...slug]/route.ts` catch-all returning 404 + JSON envelope

The API-side analog of `app/src/app/[...slug]/page.tsx` (ADR 0048). One file exporting `GET`, `POST`, `PUT`, `PATCH`, `DELETE` that all return `NextResponse.json({ error: "Not found." }, { status: 404, headers: { "Cache-Control": "no-store" } })`; `HEAD` and `OPTIONS` return an empty `NextResponse` with status 404 (no body, no JSON envelope — body-less methods don't carry a body anyway, and the 404 must match the real routes' 405-on-wrong-method pattern in shape).

Real `/api/*` routes match first (Next walks specific-to-generic); the catch-all is only reached when no real route matches, so it cannot shadow any existing route. No `Cache-Control` on the real routes is affected.

### 3. Clamp the page number in the page handler instead of redirecting

New helper `clampPageNumber(page, pageCount)` in `app/src/lib/mission-board-query.ts` (next to the existing `parseMissionBoardQuery` / `isCanonicalMissionBoardQuery` since it's the same surface area). The page computes `effectivePage = clampPageNumber(query.page, pageCount)` after the data fetch and passes `effectivePage` to `PaginatedMissionBoard` instead of `query.page`. The `redirect()` call is removed entirely; the URL bar keeps `?page=99` (which the pagination UI's own links then make canonical as the user navigates), and the page renders the correct content on the first byte. `clampPageNumber` is unit-tested in `mission-board-query.test.ts` for in-range, past-end, below-1, zero-row, and negative-count cases.

## Implementation

### Files added

- `app/src/app/api/[...slug]/route.ts` — the catch-all (Finding 2).
- `app/src/app/api/[...slug]/route.test.ts` — 7 Vitest cases asserting every method returns 404 with the right `content-type` and `Cache-Control`.

### Files modified

- `app/src/components/bookmark-toggle.tsx` — new required `repoFullName` prop; `aria-label` and `title` rewritten to include it. `app/src/components/notification-toggle.tsx` — same change, mirrored.
- `app/src/components/repo-card.tsx` — passes `repoFullName = ${repo.owner}/${repo.name}` to both toggles. `app/src/app/repo/[owner]/[name]/page.tsx` — same.
- `app/src/lib/mission-board-query.ts` — new `clampPageNumber()` export.
- `app/src/lib/mission-board-query.test.ts` — 5 new test cases for `clampPageNumber` (in-range, past-end, below-1, empty board, negative count).
- `app/src/app/missions/page.tsx` — uses `clampPageNumber`; removes the `redirect()` for `page > pageCount`; `effectivePage` flows into `PaginatedMissionBoard`.

### What didn't change

- No new dependency, no schema change, no DB migration, no query change.
- The `isCanonicalMissionBoardQuery` redirect in `missions/page.tsx` (and its sibling in `repo/[owner]/[name]/page.tsx`) is unchanged. That redirect fires for `?sort=easiest` and similar; it runs before any data fetch, so the empty-flash window is small enough that it's not a UX problem. (If the audit surfaces it as a separate issue, a follow-up can clamp `sort` and other axes the same way; out of scope here.)
- The real `/api/*` routes' 405-on-wrong-method responses are unchanged; the new catch-all is a peer, not a replacement.

## Verification

### Live verification (against `deptend.vercel.app`, post-deploy)

- `GET /` and `/missions` and `/org/SpIob` and `/repo/SpIob/FlowState` all return 200 with no error-boundary bodies.
- `POST /api/repos/precheck` (any body) returns **404** with `content-type: application/json; charset=utf-8` and body `{"error":"Not found."}`. The previous 200-with-HTML response is gone.

## Consequences

**Positive.**

- A screen-reader user navigating `/` or `/org/SpIob` now hears distinct labels for each bookmark/notification toggle. The fix is one new prop plumbed through two call sites.
- Any client that hits a mistyped `/api/*` path now gets a parseable 404 JSON response — `await res.json()` returns `{ error: "Not found." }`, the `.ok` check correctly returns false. No silent failure mode.
- `/missions?page=99` no longer flashes an empty board. The page renders correctly the first time; the URL bar keeps the user's `?page=99` input until they click a pagination link, which then carries them to the canonical URL.

**Negative.**

- One more required prop on the two toggle components. Any future caller that forgets to pass `repoFullName` will fail typecheck. (Mitigated by the prop being a plain string and both call sites already having the data in scope.)
- The `/api/[...slug]` catch-all means a typo on any `/api/*` URL is now visible in the server logs as a 404 instead of a 200-with-HTML fallthrough. That's the correct behavior, but worth noting because log volume on that shape goes from "looks like 200s" to "looks like 404s" after deploy.

**Open question / future work.**

- The `isCanonicalMissionBoardQuery` redirect (for `?sort=easiest` and similar) still uses `redirect()` and therefore the same meta-refresh-fallback path. It's a shorter window than the `page > pageCount` case (the redirect fires before the data fetch) and not the primary UX problem this audit surfaced. If a follow-up wants to remove it, the same clamp pattern would extend to `sort` / `group` / `missionType` / `q` — a different decision point.
- Library work for screen-reader acceptance testing isn't in this audit's scope. The fix is a strict improvement and tested by reading the rendered DOM (`document.querySelectorAll('button[aria-label]')` returns 4 distinct labels on `/`), but a real VoiceOver/NVDA pass is a separate task.
