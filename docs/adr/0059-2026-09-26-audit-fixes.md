## Context

Three small fixes from the 2026-09-26 audit pass (Vercel/CI/perf focus), batched in one ADR per the 0054 precedent:

1. **NaN-poisoned mission scores** (found live, not by inspection): the dependabot `actions/upload-artifact` bump PR's push CI run (36219595599, 2026-09-26) failed intermittently at `cli/src/property.test.ts:503` — `expected NaN to be greater than or equal to 0`. The property test's `epssScore` arb (`fc.option(fc.float(...))`) generates `NaN` (fast-check's float arb includes it by default; only `cvssScore`'s arb filtered it), and `ImpactInputs.epss_score: number | null` is type-valid for `NaN` — so the invariant "all missions have scores in 0–10" is the scorer's to uphold, not the test's. The old scorer multiplied the impact by `1 + NaN * 0.5` behind an `epss_score != null` guard (true for `NaN`), and `Math.min(Math.max(NaN, 0), 10)` passes `NaN` straight through (`Math.max(NaN, 0)` is `NaN`) — poisoning `impact_score`, `composite_score`, and every downstream invariant. Main's push runs passed only because the failing seed is one of 2^32.

   Root-cause fix, class-wide: a shared `clampScore()` in `packages/core/src/scorer/impact.ts` maps `NaN` → 0 (the same conservative floor as the `unknown` severity fallback) and all four clamp sites across the three scorers (`impact.ts` return, `ecosystem-value.ts` `logComponent` + return, `mission-scorer.ts` composite) now go through it. The EPSS boost additionally guards on `Number.isFinite` so a `NaN` EPSS score applies no boost rather than boosting toward a garbage value. The property test is unchanged — it caught a real bug and is the regression net. Deterministic unit tests pin the NaN path (`impact.test.ts`, EPSS boost describe block — the EPSS branch had zero unit coverage before this).

2. **No `next build` in CI**: `ci.yml` verified lint/typecheck/tests only, so a build-breaking regression in `app/` surfaced as a failed Vercel deploy (production left on the previous commit) instead of a red CI run. AGENTS.md §6's gate requires a full production build; CI didn't enforce it. New `build` job (parallel with `test`, after `lint-and-typecheck`) runs `pnpm --filter app build`. No `DATABASE_URL` is needed at build time — route modules use the lazy DB singleton (`getDb()`), verified by the local build passing with no env vars set.

3. **`X-Powered-By: Next.js` on every response**: no config removed it. Framework disclosure is recon value for an attacker and zero value for users — inconsistent with the middleware's H1 header hardening (`Referrer-Policy: no-referrer`, `Permissions-Policy` deny list, ADR 0037/0052). `poweredByHeader: false` in `app/next.config.ts`.

---

## Decision

1. `clampScore()` (NaN → 0, then 0–10 clamp) is the single clamp primitive for all three scorers; the EPSS boost fires only on finite `epss_score` values. No scoring-formula change for finite inputs — all pre-existing scorer unit tests pass unchanged.
2. CI gains a `build` job running the full Next.js production build on every push/PR.
3. `poweredByHeader: false`.

No new dependencies, no schema migration, no env vars.

---

## Consequences

**Positive.**

- A single malformed numeric input can no longer poison any mission score; `NaN` degrades to the conservative floor, consistent with how `cvss_score: null` is handled.
- Build-breaking regressions surface as red CI runs, not failed Vercel deploys (prod keeps serving old code either way, but CI now catches it before merge).
- One less framework-disclosure header on every response.

**Negative.**

- CI gains ~1–2 min per push (the build job).
- `clampScore` is exported from `impact.ts` and imported by the two sibling scorers — a new cross-module edge within `packages/core/src/scorer/` (kept inside the scorer layer; no ADR 0012 concern, which is about `/app`).
